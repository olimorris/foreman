# Foreman

You're helping someone use Foreman. This file tells you how it works, how to set it up and how to change its settings. Use Foreman's words with them: orchestrator, worker, reviewer, task, brief, decision.

## What it is

Foreman is a Claude Code plugin. One Claude session, the orchestrator, runs a small crew of worker Claude sessions on one git repo. The orchestrator never writes code. It plans, writes a brief for each task and hands it to a worker. Each worker builds one task in its own git worktree, on a branch named `foreman/<task>`, in its own tab. A reviewer checks each finished task against the user's intent. Approved work becomes a PR, and the user merges every PR themselves, unless they switch on automerge.

Tasks are named T1, T2 and so on. Workers are numbered W1, W2 and so on. Decisions are named D-1, D-2 and so on, and questions Q-1, Q-2 and so on.

## Requirements

- macOS, inside a terminal app Foreman can drive. Rex (https://www.superlogical.com) is the default. Foreman detects the terminal it's in, so `FOREMAN_TERMINAL=<name>` is only needed to override that and pick another. `foreman doctor` lists the ones available, and each terminal's setup is in its folder under `src/integrations/`.
- Claude Code 2.1.224 or later: `brew install --cask claude-code`.
- git, and gh signed in with `gh auth login`. Homebrew installs Bun, jq, fswatch and gh along with Foreman.
- Web screenshots need Playwright's Chromium: `bunx playwright install chromium`.
- macOS app screenshots need Xcode, and Screen Recording permission for the terminal in System Settings > Privacy & Security > Screen & System Audio Recording.

Install:

```sh
brew install olimorris/tap/foreman
foreman doctor
```

`foreman up` loads the plugin from the same Homebrew install, so the command and the plugin are always the same version. Foreman isn't in a Claude Code plugin marketplace, so there's nothing to install with `/plugin`.

Uninstall: `brew uninstall foreman` removes the command and the plugin, but not what Foreman made in each repo it ran in. In each of those repos:

```sh
git worktree remove --force .foreman/worktrees/<task>   # once per leftover worktree
rm -rf .foreman
git worktree prune                                       # if .foreman/ went first
git branch -D $(git branch --list 'foreman/*' | tr -d ' *+')
```

Then delete the `.foreman/` line from `.git/info/exclude`, which Foreman added to keep `.foreman/` out of git. Branches Foreman pushed and its PRs are on GitHub, so close or delete those there.

`foreman doctor` checks every requirement and names what's missing. Run it first whenever something doesn't start.

## How a run goes

1. The user opens their terminal in their repo and runs `foreman up`. This opens a terminal session named `foreman-<repo>` with the orchestrator, and a status pane beside it.
2. The user gives the orchestrator a backlog and a deadline in plain words, or points it at a file.
3. The orchestrator asks about anything unclear, then writes one plan: the tasks, what runs first, which model each task runs on and what it would cut. If each backlog item became one task, nothing is cut and no decision is open, it starts straight away and shows the plan. Otherwise it waits for the user to approve it.
4. Workers start, up to `maxWorkers` at once. A task waits for the tasks it depends on, and for any running task that owns the same files.
5. When a worker finishes, the reviewer checks it and sends feedback until it's right. Then Foreman pushes the branch and opens the PR.
6. A task that depends on one other task starts on top of that task's branch once its PR is approved and open, unless `stackTasks` is `false`. Its PR says which PR to merge first.
7. When a PR merges, Foreman removes that task's worktree and tab, asks the other workers to rebase and starts the tasks that were waiting on it.
8. At the end, Foreman writes `.foreman/summary.md`: the PRs in review order, how to test each, the assumptions to check and the calls Foreman made on its own.

The user talks to the orchestrator in its tab for anything about the plan or a task. Changing settings, checking on the run and fixing setup are things you can help with from outside.

## Why a task is waiting

`foreman status` gives each waiting task's reason. A planned task starts once all of these are true:

- A worker slot is free. At most `maxWorkers` workers run at once.
- No running task owns files that overlap its own. Each task owns the smallest set of paths it changes, so two tasks that touch the same files run one after the other.
- The tasks it depends on have merged. A task with exactly one unmerged dependency is the exception: it starts on top of that dependency's branch once its PR is approved and open, unless `stackTasks` is `false`. With two or more unmerged dependencies, it waits for them to merge.

Contract tasks go first. They're small tasks that set up a type, API or schema that other tasks share.

## Decisions

A decision is a rule that affects more than one task, like the shape of an API. Decisions are named D-1, D-2 and so on.

- Every brief points the worker at the repo's ADR folder and the decisions accepted so far.
- A worker that needs a new decision proposes it. The orchestrator accepts or rejects it. When it affects other tasks, the orchestrator asks the user first, and if they don't answer within `answerMinutes`, it decides and marks the decision as its own call.
- Accepted decisions reach every running worker straight away. They reach the repo as ADRs in one batched decisions PR, which the user merges like any other.
- A PR comment that states a rule, like "always store times in UTC", can become a decision too.
- To overrule a decision, the user tells the orchestrator, such as "overrule D-4". It rejects the decision and tells the workers.
- To see the proposed and accepted decisions, the user asks the orchestrator.

## Review

- When a worker reports done, a separate reviewer session checks the change against the user's intent. For a change to the app's screens, it takes before and after screenshots.
- If the reviewer finds problems, the same worker gets the issues, fixes them and reports done again. After two rounds of changes, the orchestrator stops and asks the user whether to send a third round, take over the task or merge it as is. Each round's screenshots are in `.foreman/tasks/<task>/review/round-<n>/`.
- Approved work becomes a PR. Its description has the user's intent, what changed, the decisions it touched, before and after screenshots, the reviewer's verdict and risk, and an AI Usage section with the task's cost. A PR built on another task's branch says which PR to merge first. When the user has a `pull-request` skill, the PR's title and opening follow it, as below.

## Steering and stopping

- For anything about the plan, such as adding, changing or cutting a task, or stopping the run, the user tells the orchestrator in its tab. There's no single command that stops everything.
- To steer one worker, the user can open its tab, named like `W1 · T1: add tags to notes`, and type to it.
- To stop one worker, the user asks the orchestrator to pause it, which closes its tab. Its commits stay on its branch and uncommitted work stays in its worktree. `foreman resume <task>` reopens its session where it left off.
- If the user closes a worker's tab, the orchestrator notices and asks whether to resume the task or tear it down. It never discards unmerged work without the user's yes.

## The CLI and the MCP server

The `foreman` CLI is for people. The orchestrator and workers call tools on Foreman's MCP server instead.

- Foreman starts the server only in the sessions it starts. It never runs in the user's own sessions or the reviewer.
- A worker gets `report`, `propose`, `note` and `tidy`. It can't run `foreman` commands.
- The orchestrator gets the rest, like `plan`, `spawn`, `deliver` and `status`.
- `foreman status` and the `status` tool share one implementation, so they agree. The same goes for `timeline`, `summary`, `cost` and `budget`.

### MCP tasks

`watch`, `baseline` and `together` run as MCP tasks. Each returns at once, and the orchestrator waits without spending tokens. When the task completes, its line wakes the orchestrator.

- While it waits, the orchestrator's tab shows "MCP task still running".
- When it completes, the tab shows "MCP task ... completed", then the orchestrator's reply. The user no longer sees a message from another session.
- The orchestrator calls `watch` again after each line. A Stop hook stops it ending a turn with tasks in flight and no watch running.
- Tasks don't survive a restart. The orchestrator calls `watch` again after one. A baseline or together check that was running is lost.

## Updating Foreman

```sh
brew upgrade foreman
```

Sessions that are already running keep working after an upgrade. Their hooks run the new version, but they keep the agents, skills and prompts they started with, so update between runs rather than in the middle of one.

## Commands for the user

`foreman help` lists these, plus `foreman hook` and `foreman mcp`, which Claude Code runs. The orchestrator and workers call Foreman's MCP tools for everything else.

- `foreman doctor`: check every requirement and name what's missing.
- `foreman --version`: print the installed version.
- `foreman up`: start the orchestrator and status pane in the current repo. Takes `--model <name>` to pick the orchestrator's model for that run.
- `foreman status`: what each task is doing, what's waiting to start and the questions waiting on the user.
- `foreman pane`: reopen the status pane beside the current tab.
- `foreman budget`: what each task has spent against its limit. `foreman cost` splits it into workers and reviews.
- `foreman budget <usd>`, `foreman budget <task> <usd>`, `foreman budget --plan <usd>`: set the limit for every task, one task, or the plan.
- `foreman workers <n>`: run up to n workers at once until the current plan finishes. The next plan goes back to `maxWorkers`. Lowering it stops no worker, and raising it starts nothing until the orchestrator starts the next tasks. `foreman workers` with no number prints the limit and where it comes from.
- `foreman resume <task>`: reopen a stopped worker's session, such as after raising its limit. Takes `--model <name>`.
- `foreman restart <task>`: close a worker and reopen its session. Takes `--model <name>`.
- `foreman summary`: write and show the run summary.
- `foreman timeline [<task>]`: what happened to each task and when, and which tasks waited on a quiet worker.
- `foreman automerge on`: let Foreman merge each task's PR once the reviewer approves it and every check passes, until the current plan finishes. The user can also tell the orchestrator "feel free to merge". It only merges task PRs from `foreman/<task>` branches, so release PRs, the decisions PR and the user's own PRs are never touched. A failing check never merges, and Foreman sends the worker to fix it. The `never` list still applies: the reviewer won't approve a PR that a rule about merging covers. A PR built on another task's branch waits until that task merges. Merges use squash when the repo allows it, then a merge commit, then rebase. `foreman automerge off` hands merging back, and `foreman automerge` prints whether it's on. `foreman status` shows "Automerge on" while it is.
- `foreman notes`, `foreman note "<fact>"`, `foreman note --remove <n>`: list, add or remove known problems every worker should know about, such as a test that deadlocks.

The watcher, the baseline, the `together` check and tidying a task's leftover processes are the orchestrator's jobs. When the user wants one done, they ask the orchestrator.

## Settings

Settings live in `.foreman/config.json` in the user's repo. The file is plain JSON, so it can't hold comments. Every key is optional. Foreman writes some keys itself, so edit the file in place and keep the keys already there.

- `maxWorkers` (number, default 3): how many workers run at once. The plugin option of the same name sets it for every repo, and this key overrides it. `foreman workers <n>` overrides both until the current plan finishes.
- `budget` (object, default `{ "perTask": 5, "plan": 40 }`): spend limits in US dollars. `perTask` covers each task's worker and its reviews. `plan` covers every task plus the orchestrator. `tasks` maps a task to its own limit, like `{ "T3": 15 }`. Keys you leave out keep their defaults. `foreman budget` writes this key for you.
- `workerModel` (string): the model a task runs on when the plan doesn't name one. Takes an alias like `"sonnet"` or a full model id like `"claude-sonnet-5-5"`. Without it, workers use Claude Code's default model.
- `orchestratorModel` (string): the model `foreman up` starts the orchestrator on. `foreman up --model <name>` overrides it for one run. Without it, Claude Code's default.
- `reviewerModel` (string): the model the reviewer runs on. Without it, Claude Code's default.
- `stackTasks` (boolean, default true): `false` makes a task wait for its dependency to merge, instead of starting on top of its approved PR.
- `answerMinutes` (number, default 30): how long the orchestrator waits for the user to answer a question before it goes ahead with the call it said it would make. `0` makes it always wait.
- `stallMinutes` (number, default 20): how long a worker can go without replying, while its commands use no CPU, before Foreman nudges it.
- `test` (string): the command that runs the repo's tests, like `"swift test"`. Foreman runs it in a fresh checkout for the baseline and the `together` check, so include any setup, like `"bun install && bun test"`. The orchestrator works it out and saves it when it plans, if it's missing.
- `testMinutes` (number, default 15): how long one test run can take before Foreman stops it as hung. Raise it for a slow suite.
- `screenshots` (object): how to run the app for before and after screenshots. See below.
- `prScreenshots` (`"local"` or `"branch"`, default `"local"`): `"local"` keeps screenshots on the user's machine and lists their paths in the PR. `"branch"` pushes them to a `foreman-screenshots` branch so they show in the PR on GitHub.
- `never` (array of strings): things Foreman must never do in this repo, one plain sentence each, like `"Merge a release PR. The user cuts every release."`. The orchestrator gets the list in its session-start context and follows it above any other instruction. Every new brief lists it, and the reviewer treats a change that breaks one as an issue. An empty or missing list adds nothing. Nothing blocks these actions yet, so the list relies on each session following it.
- `telegram` (object): turns on pings through Claude Code's Telegram plugin, like `{ "when": "only when a question has waited 10 minutes, or the run is finished" }`. `when` is free text in the user's own words, and the orchestrator gets it in its session-start context. Without `when`, the orchestrator pings when a question needs the user's answer or the run is finished. Without `telegram`, nothing changes. See "Telegram" below for setting up the plugin.
- `prices` (object): prices for models Foreman doesn't know, so it can work out their cost. Maps a model id to dollars per million tokens: `{ "my-model": { "input": 3, "output": 15, "cacheRead": 0.3 } }`. Foreman already knows claude-fable-5-2, claude-opus-5-5, claude-sonnet-5-5 and claude-haiku-5-5.
- `context` (string): the path to the repo's glossary of domain terms, which every brief points workers at. Foreman finds `CONTEXT.md` or `docs/CONTEXT.md` on its own.
- `adr` (object): how the repo writes its architecture decision records. The orchestrator fills it in from the repo's ADR folder, or sets up a new one. Don't write it by hand.

### Screenshots

The reviewer takes screenshots of the screens a task changes, before and after, and puts them in the PR. The orchestrator lists those screens in each brief. Each task's app runs from its own worktree, so tasks never share a server or an app's data.

For a web app:

```json
{ "screenshots": { "adapter": "web", "start": "npm run dev -- --port {port}", "url": "http://localhost:{port}" } }
```

- `start` (required): the command that starts the dev server. Foreman replaces `{port}` with a free port.
- `url` (required): where the app answers, with the same `{port}`.
- `install`: a command to run in the worktree first, like `"npm install"`.
- `viewport` (default `"1280,800"`): the browser's width and height.
- `readySeconds` (default 120): how long to wait for the URL to answer.

For a macOS app:

```json
{ "screenshots": { "adapter": "macos", "build": "xcodebuild -scheme App -derivedDataPath {derivedData} build", "app": "{derivedData}/Build/Products/Debug/App.app" } }
```

- `build` (required): the command that builds the app. Foreman replaces `{derivedData}` with a folder of its own for each task.
- `app` (required): the path to the built `.app`, with the same `{derivedData}`.
- `prepare`: a command to run in the worktree before the build, like generating the Xcode project.
- `settleSeconds` (default 5): how long to wait after launch before the screenshot.
- `env`: environment variables for the app, like `{ "UI_TESTING": "1" }`.

Each copy of a macOS app runs with its own bundle id and home folder, so screenshots never touch the user's real app data.

## Telegram

With `telegram` set in `.foreman/config.json`, the orchestrator pings the user through Claude Code's official Telegram plugin, and the user can answer from Telegram. Set it up once:

1. The user creates a bot: they message @BotFather on Telegram, send `/newbot` and copy the token.
2. In any Claude Code session: `/plugin install telegram@claude-plugins-official`, then `/telegram:configure <token>`. The token goes to `~/.claude/channels/telegram/.env`.
3. Add `telegram` to `.foreman/config.json` with the user's own words for when to ping.
4. Run `foreman up`. The user DMs the bot, which replies with a pairing code, and runs `/telegram:access pair <code>` in the orchestrator's tab. Pings start straight away, with no restart, because the orchestrator reads the paired chat from the plugin's `access.json`. After that, `/telegram:access policy allowlist` stops strangers getting pairing codes.
5. `foreman doctor` checks the plugin is installed, has a token and is paired.

How it works:

- `foreman up` starts the orchestrator with `--channels plugin:<the installed plugin>`, which lets messages from Telegram reach it. The plugin may be installed as `telegram@claude-plugins-official` or `telegram@anthropic-plugin-directory`, and Foreman uses whichever is installed.
- Only one session at a time can own the bot. Each session that loads the plugin starts its own bot and stops the one already running. So workers and the reviewer always start with the plugin turned off, whether or not `telegram` is set. Any other Claude Code session the user opens with the plugin on will take the bot from the orchestrator until the orchestrator restarts.
- The orchestrator pings with the plugin's `reply` tool when the `when` text matches, in a line or two that names the task and worker. A message from Telegram counts as the user's own words, the same as typing in the orchestrator's tab.
- Messages from Telegram need the user's Claude Code account to allow channels. Some Team and Enterprise organisations turn them off. Pings still go out without them, but answers have to go in the orchestrator's tab.

## What Foreman does on its own

- **Over budget.** Foreman checks spend at least every 30 seconds. A task over its limit has its worker stopped, and the orchestrator asks the user whether to raise the limit. When the plan goes over, every worker stops and no new task starts. Work already committed stays on the task's branch, and uncommitted work stays in its worktree. Costs use Anthropic's list prices, so on a subscription they show how much work was done, not what the user pays.
- **Usage limit.** On Pro, Max and other Claude subscriptions, every worker, reviewer and the orchestrator share the account's usage limit. When a worker hits it, the watcher pauses every running worker by closing its tab, starts no new task and holds reviews. A review that hits the limit waits for the reset and runs again. At the reset time, the watcher reopens each paused worker and tells it to carry on where it was. Uncommitted work stays in each worktree. `foreman status`, the status pane and `foreman timeline` show the wait and the reset time. Dollar budgets still apply on a subscription, but they measure how much work was done at list prices, not what the user pays, so a user who only cares about the limit can raise them with `foreman budget`.
- **Hung workers.** After `stallMinutes` with no reply and no CPU use, Foreman messages the worker and names the command that looks hung. At twice that, it restarts the worker in a new tab. A worker whose commands keep using CPU, like a long build, is left alone until four times `stallMinutes`. After two restarts, the orchestrator steps in.
- **Permission blocks.** When auto mode refuses a worker's call, or a worker waits at a permission prompt in its tab, Foreman records it from Claude Code's PermissionRequest and PermissionDenied hooks and the worker's transcript. A reviewer's refusals come from its `claude -p` output. The orchestrator tells the user which session was blocked, from what, and the rule to add in /permissions, such as `Bash(gh pr merge *)`, or that they can say skip it. The worker carries on with what doesn't need that step. `foreman status` and the pane list the block under "Needs you" until the user answers a prompt in the worker's tab, the call later runs, or the orchestrator closes it. A worker waiting at a prompt is never nudged or restarted. Blocks live in `.foreman/blocks.json`.
- **Leftover processes.** Foreman stops any process in a worktree whose parent has exited, such as a test runner left behind by a timed-out run. Anything else open in the worktree, like the user's shell or editor, is left alone.
- **Unanswered questions.** The orchestrator tells the user the call it would make. If they don't answer within `answerMinutes`, it makes that call and the summary lists it. It never does this for money or lost work: raising a budget, discarding unmerged work, or closing or merging a PR always waits for the user.
- **PRs that clash.** Once two or more PRs are open, Foreman merges them into a throwaway copy of the base branch and runs `test`. It reports PRs that conflict, the order to merge them in and tests that fail only when they're combined.

## The user's own skills

Skills go in `.foreman/skills/<name>/SKILL.md`, in Claude Code's skill format. Every session gets them, and they stay out of git.

- Workers and the orchestrator load them as `user-skills:<name>`, from a plugin folder that links to `.foreman/skills`. Nothing is copied into a worktree. It's a plugin folder because Team and Enterprise logins turn off skills from MCP servers.
- The reviewer checks each change against the skills whose description fits reviewing code.
- A `pull-request` skill shapes the PRs Foreman opens. Foreman adds its own sections after the description.
- An `adr` skill shapes the decisions it records, unless the repo's ADR folder already has its own convention.
- A skill is named by its folder, not its frontmatter.
- A skill added mid-run reaches workers started after it, and the reviewer from its next review.

Start from Foreman's own pull-request skill:

```sh
mkdir -p .foreman/skills/pull-request && curl -fsSL https://raw.githubusercontent.com/olimorris/foreman/main/.claude/skills/pull-request/SKILL.md -o .foreman/skills/pull-request/SKILL.md
```

## Where things live

- `.foreman/` in the user's repo holds every bit of Foreman's state. Foreman keeps it out of git. If the orchestrator restarts, it picks up from there.
- `.foreman/config.json` and `.foreman/skills/` are the only things in there for people to edit. Change the rest through `foreman` commands.
- `.foreman/summary.md` is the run summary.
- `.foreman/worktrees/<task>` is each task's worktree.
- The repo's ADR folder, such as `docs/decisions` or `docs/adr`, holds the decisions that have merged.

## When something goes wrong

- Something won't start: run `foreman doctor`.
- Telegram pings stopped: another Claude Code session with the Telegram plugin on took the bot. Close it, then restart the orchestrator.
- `foreman up` says the session already exists: the orchestrator is already running in that terminal session. Switch to it in your terminal.
- The status pane is gone: run `foreman pane` from the orchestrator's tab.
- A task stopped over budget: `foreman budget <task> <usd>`, then `foreman resume <task>`.
- The orchestrator sits idle with tasks in flight: tell it to call `watch`.
- The orchestrator's turn hangs on `watch`: unset `CLAUDE_CODE_DISABLE_MCP_TASK_BACKGROUND`, `CLAUDE_CODE_MCP_AUTO_BACKGROUND_MS`, `MCP_SDK_GENERATION` and `MCP_PROTOCOL_NEGOTIATION`. Each one stops MCP tasks running in the background.
- A worker seems stuck: `foreman timeline <task>` shows when it went quiet. Foreman restarts hung workers itself, and `foreman restart <task>` does it by hand.
- Tests hang or fail on the base branch: `foreman note "<what happens and how to avoid it>"` tells every worker. Ask the orchestrator to run the baseline again to check the base branch.
- The `together` check says tests ran too long: raise `testMinutes`.
